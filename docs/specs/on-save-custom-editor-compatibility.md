# 保存 Markdown 时的代码块格式化兼容性（已审核）

## Problem Statement

用户在 VS Code 中用 MEO Enhanced 的自定义编辑器编辑 Markdown，并启用 Markdown Code Assistant 的 `onSave` 格式化。保存时，即使文档只有正文或 `text` 代码块，插件仍可能弹出“Open a Markdown file to format”等提示，打断编辑。当前修复又暴露了保存持久化回归：有代码块被格式化时，MEO Enhanced 的未保存圆点持续存在，用户重复按保存键也无法完成保存。

当前代码的保存监听器已经收到被保存的 Markdown `TextDocument`，但随后调用的“格式化所有代码块”命令重新读取 `activeTextEditor`。自定义编辑器可能没有对应的活动文本编辑器，因而出现错误提示。即使有活动文本编辑器，不支持格式化的 `text` 代码块也可能被统计为“已经格式化”，触发无意义的提示。此外，保存的是一个文档、活动编辑器却指向另一个文档时，当前流程可能处理错误的对象。

保存持久化回归已有用户截图和保存事件入口的红色回归测试：`onDidSaveTextDocument` 在磁盘写入之后才执行，随后的 `WorkspaceEdit` 只改了编辑器缓冲区，使文档重新变脏。MEO Enhanced 0.3.33 的本地代码表明，它调用标准 `TextDocument.save()`，保存后会核对磁盘内容与请求版本；因此保存后的编辑也可能与它的读回校验竞争。

## Solution

启用 `onSave` 时，在同一次 VS Code 保存事务中，以将要保存的 Markdown 文档为处理对象并返回代码块格式化编辑，使格式化后的内容落盘且未保存标记消失。只对启用且有已注册格式化器的代码块尝试格式化；没有符合条件的代码块时静默结束，不生成编辑，也不弹出错误、警告或“已格式化”提示。仅改动相应代码块内容，保留围栏和其他文本。格式化失败或工具不可用时，沿用真实错误反馈；不能为了格式化而无限阻塞保存。

MEO Enhanced 0.3.33 另有严格的保存确认：它要求磁盘内容与保存前提交的 webview 文本完全相同。保存前格式化虽然能正确写盘，仍会被该版本判为失败。用户明确限定本次只修改 Markdown Code Assistant，因此仅在当前活动标签页是该文档的 MEO 自定义编辑器时跳过自动格式化；从原生文本编辑器保存仍在写盘前格式化，即使同一文件也在后台 MEO 标签页中打开。MEO 中“同一次保存自动格式化且通过其校验”的完整目标在此约束下尚未达成。

## User Stories

1. 作为 MEO Enhanced 用户，我希望保存只有正文的 Markdown 时不出现格式化提示，以便继续编辑。
2. 作为 MEO Enhanced 用户，我希望保存只有 `text` 代码块的 Markdown 时静默跳过，以免插件把说明文字当作可格式化代码。
3. 作为 MEO Enhanced 用户，我希望在没有活动文本编辑器时仍能正常保存 Markdown，以免看到“打开 Markdown 文件”的误报。
4. 作为 MEO Enhanced 用户，我希望有受支持代码块时插件使用我刚保存的文档，以免格式化失效或改到别的文件。
5. 作为普通 Markdown 文本编辑器用户，我希望保存时现有的代码块格式化继续生效，以免兼容性修复造成回归。
6. 作为同时打开多个文档的用户，我希望保存文档 A 时只可能修改 A，即使活动编辑器显示的是 B。
7. 作为 Markdown 作者，我希望未启用或没有已注册格式化器的语言被跳过，以免内容被错误修改。
8. 作为 Markdown 作者，我希望语言别名遵循现有解析和注册规则，以免 `py`、`bash` 等标签失去原有支持。
9. 作为 Markdown 作者，我希望忽略指令仍然有效，以免故意保留的示例代码被格式化。
10. 作为 Markdown 作者，我希望格式化只改变符合条件的代码块内容，以免标题、正文和围栏受影响。
11. 作为 Markdown 作者，我希望代码已经符合格式时不产生编辑，以免保存后出现不必要的脏状态。
12. 作为开启保存时诊断的用户，我希望诊断仍基于被保存的 Markdown 文档运行，以免此次修改破坏诊断流程。
13. 作为使用手动格式化命令的用户，我希望该命令的交互提示继续有用，以便主动执行时知道处理结果。
14. 作为只开启 `onCommand` 或 `onType` 的用户，我希望保存行为不因本次改动而额外触发格式化。
15. 作为自行维护插件版本的用户，我希望修复可在本地构建、打包并安装，以便不依赖 Marketplace 发布。
16. 作为 MEO Enhanced 用户，我希望一次保存就把格式化后的代码写入磁盘并清除未保存圆点，以免进入重复保存循环或丢失修改。

## Implementation Decisions

- **改动边界：** 仅 Markdown Code Assistant 的保存触发流程。复用现有代码块提取、格式化器注册表、分发器和格式化摘要；手动命令继续用 `WorkspaceEdit`，普通编辑器自动保存路径通过 VS Code 保存前的 `TextEdit[]` 加入同一次磁盘写入。不增加格式化引擎或依赖。
- **技术依据：** 文档格式化入口已能直接接收 `TextDocument` 并返回编辑。保存前事件的 `waitUntil` 可把异步生成的 `TextEdit[]` 纳入保存事务，但必须在事件监听器同步阶段调用。手动命令仍可从活动编辑器取得文档，并维持其主动操作的反馈语义；保存后事件只保留诊断等不改文档的工作。
- **方案比较：** 方案 A 继续在保存后 `WorkspaceEdit` 并再次调用 `save()`，改动少，但有重入、重复保存和 MEO 版本校验竞争风险。方案 B 对所有编辑器使用 `waitUntil(TextEdit[])`，普通编辑器可正确落盘，但 MEO 0.3.33 会拒绝变化后的磁盘内容。方案 C 仅对非 MEO 文档使用保存前编辑，MEO 文档跳过自动格式化；实现范围最小且保存可靠，但 MEO 的自动格式化目标暂未达成。按用户限定的仓库范围采用方案 C。
- **资格判定：** `text`、无语言标签、未启用语言、无已注册格式化器的语言，以及由忽略指令排除的代码块，不构成这次保存的可格式化工作。已有语言别名仍按现有规则解析。格式化器已注册但运行时不可用属于真实失败，继续走现有错误处理。
- **无操作反馈：** 自动保存路径在无可格式化代码块、结果未变化时不显示信息或警告，不调用写回。手动命令的结果提示不因自动保存的静默规则而一并删除。
- **写回目标：** 只把将要保存的文档中实际变化的代码块编辑交给当前保存事务，不对活动编辑器中的其他文档应用编辑，也不在保存后再次写入该文档。若保存前期间文档版本变化，避免应用基于旧版本的编辑。
- **配置与兼容：** 保留现有触发模式、启用语言、命令标识、格式化器优先级与诊断流程。本次不改 `onType` 的触发设计。
- **文档同步大纲：** 审核通过并实施时，更新用户文档中的 `onSave` 行为及自定义编辑器支持条件，并在架构文档中说明保存事件文档与手动命令文档的来源区别及已验证的限制。

## Testing Decisions

- 好测试只断言用户可见行为与编辑目标：有没有提示、有没有实际编辑、改动落在哪个文档、内容是否正确。不要断言内部调用次数或私有函数拆分方式。
- 优先在**扩展保存事件这一最高现有入口**做一组行为测试，使用仓库已有的 VS Code Jest mock；模拟保存前编辑、磁盘写入、保存后通知的顺序，并断言最终磁盘内容和脏状态。只有入口难以覆盖的具体格式化结果，才在现有文档格式化入口补测试。尽量不新增生产代码测试接口。
- 覆盖 Markdown 正文、仅 `text` 块、无语言块、未启用语言、受支持语言、已符合格式、混合块，以及保存 A 但活动编辑器为 B 或不存在的情形。
- 覆盖非 Markdown 保存不触发处理、`onCommand` 模式保存不触发、保存时诊断仍收到被保存文档，以及手动格式化命令没有回归。
- 沿用现有代码块提取器测试和 Markdown fixture 的风格；在当前仓库测试 MEO 自定义标签页的保存不生成格式化编辑，其他文档仍正常格式化。扩展开发宿主中还须手动验证 MEO 保存后磁盘内容正确、未保存圆点消失、再次保存不会循环。
- 通过类型检查、lint、现有测试和构建；在手动场景确认 VSIX 可打包和本地安装。打包安装属于交付验证，不代表自动发布。

## Out of Scope

- 修改 MEO Enhanced 的源码、私有 API 或 CodeMirror 内部状态。
- 保证未通过标准 `TextDocument` 保存事件暴露的 MEO 内容也能自动格式化。
- 修改 `onType` 触发、单个代码块手动命令、诊断规则、格式化引擎、语言支持范围或插件身份。
- 向 VS Code Marketplace 发布、追溯当前 Marketplace VSIX 的精确构建 commit、合并 `engine-integration` 分支或向上游提交 PR。
